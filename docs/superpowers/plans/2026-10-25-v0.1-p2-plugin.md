# YoungCrow v0.1, P2: plugin para Claude Code e Codex

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publicar as skills, o agente e os hooks do núcleo como o plugin `youngcrow`, instalável no Claude Code e no Codex a partir deste repositório, e ligar o `youngcrow init` a ele.

**Architecture:** `tools/build_plugin.py` gera `plugins/youngcrow/` e os arquivos derivados do pacote a partir das fontes atuais (`skills/`, `.claude/agents/`, `.codex/agents/`, `scripts/source_prompt.py`), com teste de frescor como o da tabela de hashes do P1. Um único `.claude-plugin/marketplace.json` serve os dois clientes; o plugin tem manifesto para cada um. Os hooks do plugin só executam código do próprio plugin e tratam o projeto como dado. O `init` grava a ligação do Claude no `.claude/settings.json` do projeto, escreve o agente do Codex e o catálogo de capacidades, e mostra os comandos do Codex.

**Tech Stack:** Python 3.11+ (stdlib), unittest, Claude Code 2.1.310 (`claude plugin validate`, instalação real), Codex CLI 0.164.0 (instalação real), GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-24-v0.1-open-source-decisions.md`. Roteiro e P1: `docs/superpowers/plans/2026-10-24-v0.1-open-source.md`.

**Fontes oficiais conferidas em 2026-10-25:**
- Claude Code: `https://code.claude.com/docs/en/plugins-reference`, `.../plugins/marketplace-reference`, `.../hooks.md`, `.../settings-reference`, `.../plugins/cli-reference.md`, `.../sub-agents.md`.
- Codex: código de `github.com/openai/codex` no commit `970111f6` (`core-plugins/src/marketplace.rs`, `marketplace_tests.rs`, `plugin_bundle_archive.rs`, `hooks/src/engine/discovery.rs`) e `https://developers.openai.com/codex/subagents`. ## Global Constraints

Valem todas as do roteiro, mais:

- Marketplace `youngcrow`, plugin `youngcrow`, identificador `youngcrow@youngcrow`, origem GitHub `Matheusrpc/YoungCrowHarness`.
- O `version` dos dois manifestos do plugin é exatamente `youngcrow.__version__` (hoje `0.1.0.dev0`); o Claude não exige semver.
- Skills do núcleo, exatamente: `govern-capabilities`, `ingest-source`, `integrate-from-docs`, `personalizer`, `retrieve-memory`. As `yc-*` ficam para o P7; `humanizer-ptbr` fica fora (skills só em inglês).
- Hook do plugin nunca executa arquivo do projeto, nunca escreve e sempre termina com código 0.
- O `init` não escreve fora do projeto: nada em `~/.claude` nem em `~/.codex`.
- Layout do `.youngcrow/` ganha `capabilities.json` e `originals/` (emenda à restrição de layout do roteiro).
- Arquivos gerados nunca são editados à mão: muda-se a fonte e roda-se `python3 tools/build_plugin.py`.

## Decisões deste plano

Cada uma com o custo de estar errada.

- **R33** Uma fonte só: o plugin é gerado de `skills/` e dos agentes atuais, que continuam servindo o `setup.sh` até o P6. Custo: um gerador a mais para manter.
- **R34** Um `.claude-plugin/marketplace.json` com `"source": "./plugins/youngcrow"` serve os dois clientes (o Codex lê esse caminho e aceita origem em texto, `marketplace_tests.rs`). O plugin tem `.claude-plugin/plugin.json` e `.codex-plugin/plugin.json`, porque o empacotamento do Codex exige o segundo (`plugin_bundle_archive.rs`). Custo: se o Codex parar de ler o caminho do Claude, acrescenta-se `.agents/plugins/marketplace.json`.
- **R35** Os hooks rodam a cópia de `source_prompt.py` que vem no plugin e leem o projeto só como dado. Motivo: no Codex o plugin é instalado por usuário, então o hook dispara em qualquer repositório aberto; executar `.youngcrow/scripts/` de um repositório desconhecido seria execução de código alheio. Custo: plugin e projeto em versões diferentes usam o `source_prompt` do plugin (o aviso de versão cobre isso).
- **R36** O `init` liga o Claude pelo projeto (`extraKnownMarketplaces` e `enabledPlugins` no `.claude/settings.json`, valem depois da confiança no workspace) e só mostra os comandos do Codex, que instala por usuário. Custo: quem usa Codex roda dois comandos e confia nos hooks em `/hooks`.
- **R37** Ao mexer num `.claude/settings.json` que já existia, o `init` guarda os bytes originais em `.youngcrow/originals/.claude/settings.json`. O `undo` devolve esses bytes se o arquivo não mudou depois do `init`; se mudou, tira só as nossas chaves e lista o arquivo em `kept_modified`. Custo: uma cópia do arquivo no projeto, com a mesma sensibilidade do original.
- **R38** A origem do marketplace não fixa `ref` enquanto a branch `stable` não existe; o P6 acrescenta `"ref": "stable"`. Custo: uma constante no P6.
- **R39** O agente do plugin não pré-carrega skill (`skills:` sai do frontmatter); o texto manda usar a skill `integrate-from-docs`. Motivo: a documentação não diz como um agente de plugin nomeia a skill do mesmo plugin. Custo: uma chamada de skill a mais.
- **R40** O comando dos hooks é `python3 … || python …` no shell, e `commandWindows` usa `python -c` lendo `PLUGIN_ROOT`/`CLAUDE_PLUGIN_ROOT` do ambiente. Custo: uma linha longa no `hooks.json`.
- **R41** O `migrate` tira dos `.claude/settings.json` e `.codex/hooks.json` antigos só as entradas de hook cujo comando é igual a um comando publicado do `source_prompt`; sem isso, o hook antigo falharia a cada prompt depois que o `scripts/` some. Custo: um arquivo gerado a mais (`legacy_hooks.json`).

Mantém as outras chaves e a ordem, escreve com `indent=2` e quebra final, e mantém CRLF se o original usava;
  - `remove_wiring(data: bytes) -> bytes | None`: tira as subchaves que ainda têm o nosso valor e as chaves de topo que ficaram vazias. Devolve `None` quando sobra `{}`.
- `Report` ganha `next_steps: list[str]`, incluído em `to_json`. A CLI imprime os passos depois das listas.
- Manifest: `json_edits` lista `.claude/settings.json` quando o `init` mudou o arquivo. O original pré-existente vai para `.youngcrow/originals/.claude/settings.json`, registrado em `files` e `created`.

- `init` com `client` claude ou both: aplica `add_wiring`.
