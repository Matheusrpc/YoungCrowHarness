# Plugin youngcrow no Claude Code e no Codex

Frente: P2 (plugin para Claude Code e Codex), Task 6: corrida de prova, CI e guia. Plano:
[P2](../superpowers/plans/2026-10-25-v0.1-p2-plugin.md). Medição: [recibo da prova](../medicoes/2026-10-25-p2-plugin.json) e
[recibo da primeira corrida](../medicoes/2026-10-25-p2-plugin-run1-step6.json), a que falhou no passo 6.

Com o Claude Code 2.1.310 e o Codex CLI 0.164.0, o plugin `youngcrow@youngcrow` foi validado e instalado
nos dois clientes a partir deste checkout, usado como marketplace local. Cada cliente rodou o hook do
plugin num prompt que cita uma URL, e o `undo --confirm` deixou o projeto vazio. Os 28 checks do recibo
passaram. Nenhum processo ficou vivo, e o repositório terminou como começou. A prova não chamou modelo:
quando um cliente rodou o hook, a requisição foi para um servidor em `127.0.0.1` que responde 400.

## Como a prova roda

`tests/smoke_plugin.py` fica fora do `unittest discover`, como o `smoke_clients.py`. Ele cria uma pasta
temporária e dá aos clientes um `HOME`, um `CLAUDE_CONFIG_DIR` e um `CODEX_HOME` descartáveis. Os clientes
recebem só as variáveis do sistema e o `PATH`, sem proxy e sem credencial. As variáveis de proxy vão só
para o `uv build` e o `uvx`, porque o build baixa o hatchling. Cada processo roda no seu próprio grupo e
para no `finally`, também quando um passo falha. No fim, o script procura em `/proc/*/environ` qualquer
processo que ainda leve a pasta temporária e o lista em `processes_left`.

Para repetir:

```bash
npm install --prefix /pasta/descartavel @openai/codex@0.164.0
python3 tests/smoke_plugin.py --claude /caminho/do/claude \
  --codex /pasta/descartavel/node_modules/.bin/codex --json
```

O recibo tem as versões dos clientes, o HEAD e o hash do próprio script. Cada comando vem com argv, pasta
e código de saída, junto com cada check. Os caminhos aparecem como `$TMP` (a pasta temporária) e `$REPO`
(este repositório).

## O que a corrida mudou

A primeira corrida falhou no passo 6. O [recibo dela](../medicoes/2026-10-25-p2-plugin-run1-step6.json)
tem `head` `827bfbb`, `ok: false` e `failed: "the project folder is empty"`. No check do passo 6,
`detail.left` é `[".claude", ".claude/settings.json"]`, `detail.kept_modified` é `[".claude/settings.json"]`
e o arquivo ficou com `{}\n`. O script da prova não escreve nesse arquivo.

O recibo final mede o `claude plugin install --scope project` no passo 3, em `observations`. O
`sha256_before` é `88b92216…`, o hash dos bytes que o `init` grava num projeto novo (`add_wiring(None)`).
Depois do comando, `sha256_after` é `3d7a6816…`, com `bytes_changed: true`, `keys_before`
`["extraKnownMarketplaces", "enabledPlugins"]`, `keys_after` `["enabledPlugins", "extraKnownMarketplaces"]`
e `same_value: true`. O Claude reescreve o arquivo com o mesmo valor JSON em outra ordem, e o `undo`
comparava bytes. O check «claude plugin install keeps the JSON value of .claude/settings.json» falha se
uma versão futura do Claude mudar o valor. O `bytes_changed` fica só como observação, então a prova
continua passando se o Claude deixar de reescrever.

A decisão R52 (emenda à R37) resolveu isso no commit `db472f1`. Num arquivo de `json_edits`, o `undo`
recalcula os bytes que o `init` escreveu (`add_wiring` sobre a cópia guardada, ou sobre nada quando o
`init` criou o arquivo). Ele só confia nesses bytes quando o hash bate com o do manifesto. Se o arquivo
atual tem o mesmo valor JSON, conta como não mudado: o arquivo criado pelo `init` é apagado, e o que já
existia volta aos bytes originais. Uma edição de verdade continua no caminho da R49: saem só os pares
que o `init` pôs, e o arquivo aparece em `kept_modified`. Os testes novos cobrem o arquivo criado e
reordenado, o original em CRLF que volta byte a byte, a edição real depois da reordenação, a cópia
guardada alterada à mão e os bytes recalculados que não batem com o hash. Os dois últimos foram conferidos
com mutação: tirando cada guarda, o teste dela falha.

A R34 previa acrescentar `.agents/plugins/marketplace.json` se o Codex não lesse o marketplace do Claude.
Não foi preciso: o `codex plugin list` mostra que o Codex 0.164.0 lê `.claude-plugin/marketplace.json`.

## Outros fatos medidos

- O Codex troca `${CLAUDE_PLUGIN_ROOT}` no `command` do hook pelo caminho da cópia instalada
  (`$CODEX_HOME/plugins/cache/youngcrow/youngcrow/0.1.0.dev0`), como mostra o `hooks/list`.
- O Codex guarda a confiança de um hook no `config.toml`, em `[hooks.state."<chave>"]`, com `trusted_hash` e
  `trusted_content_hash`, as duas metades do `currentHash` que o `hooks/list` informa. Um hash que não bate
  aparece como `modified`.
- A confiança no projeto (`trust_level = "trusted"`) só é necessária para o agente do projeto
  (`.codex/agents/integration-specialist.toml`). As skills e os hooks do plugin não dependem dela.
- Nos dois clientes, as skills aparecem como `youngcrow:<skill>`. No Claude, o agente aparece como
  `youngcrow:integration-specialist`.
- Com um marketplace local, o Claude lê o plugin direto da pasta (`readFromFolder` no `claude plugin list`).
  A cópia em `CLAUDE_CONFIG_DIR/plugins/cache/...` é igual, e foi dela que a prova rodou o hook no passo 5.
- O Codex escreve um aviso em stderr a cada comando quando o `CODEX_HOME` fica em `/tmp` («Refusing to
  create helper binaries under temporary dir»). O aviso não muda o resultado.
- O Claude grava `remote-settings.json` e `policy-limits.json` na configuração descartável, mesmo com
  `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`. Como os clientes rodaram sem proxy, nada saiu da máquina.
- O `claude plugin validate` passa e deixa uma recomendação: o README não tem a linha que instala o plugin
  pelo marketplace. O README é reescrito no P5.

## CI e guia

O job `package` ganhou dois passos. Nos dois sistemas, `python tools/build_plugin.py --check` confere se
os arquivos gerados estão em dia. Só no Linux, `npx --yes @anthropic-ai/claude-code@2.1.310 plugin validate .`
roda com o Node 24 do `actions/setup-node` fixado, porque o Claude Code 2.1.310 pede Node 22 ou mais novo.
O comando foi medido aqui com saída 0. Os passos ainda não rodaram no GitHub Actions; rodam no PR.

O `docs/USAGE.md` ganhou, em português e em inglês, a seção sobre o plugin nos dois clientes. Ela cobre a
instalação, a confiança nos hooks, o aviso de versão, o limite do Codex (instalação por usuário) e o que o
`undo` deixa em cada cliente. Também traz a frase da R52 sobre o `undo` e, em «Rodar antes do lançamento»,
o marketplace local, a prova e os passos novos do CI.

## O que ficou sem medir

- Os hooks do Claude no Windows real. O `commandWindows` só rodou no Linux, com o interpretador dos testes
  (Task 2), e a prova inteira também só rodou no Linux.
- As páginas de plugins do Codex em `developers.openai.com`, bloqueadas nesta rede. O que o plano tirou
  delas vale só no que a corrida mediu.
- A tela `/hooks` do Codex. A confiança foi gravada direto no `config.toml` descartável, no formato que o
  `hooks/list` confere, e não pela tela.
- O aviso de confiança interativo do Claude, que é o caminho que o `init` indica. O `claude -p` não mostra
  esse aviso. Também não foi medido se a instalação por esse caminho reescreve o `.claude/settings.json`
  como o `claude plugin install` reescreve. Se reescrever, a R52 cobre o caso.
- A instalação a partir do GitHub (`Matheusrpc/YoungCrowHarness`). Ela só vale depois do merge na `main`, e a
  prova usou o checkout local.
- O aviso de versão diferente dentro dos clientes. A corrida só mostrou que, com as versões iguais, o hook
  fica quieto; o aviso tem teste unitário (Task 2).

## English

Claude Code 2.1.310 and Codex CLI 0.164.0 validated and installed the `youngcrow@youngcrow` plugin from
this checkout as a local marketplace. Each client ran the plugin hook on a prompt that cites a URL. The
request went to a loopback fixture, so no model was called. `undo --confirm` left the project empty. All
28 checks in the receipt passed, no process was left, and the repository was unchanged. The first run (its
receipt is committed too) failed at undo: `claude plugin install --scope project` rewrites
`.claude/settings.json` with the same value in another key order, which the final receipt records as
`bytes_changed: true` and `same_value: true`. Ruling R52 makes undo compare JSON values against the bytes
init wrote, recomputed and checked against the manifest hash. Codex reads
`.claude-plugin/marketplace.json`, so the R34 fallback was not needed. CI now checks the generated plugin
files on both systems and runs `claude plugin validate .` on Linux. Not measured: Claude hooks on real
Windows, the blocked Codex plugin docs, the Codex `/hooks` screen (trust was written straight into the
throwaway config), the interactive Claude trust prompt, and the GitHub install before the merge.
